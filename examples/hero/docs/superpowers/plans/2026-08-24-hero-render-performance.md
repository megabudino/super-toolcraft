## 1. Корзина A — побайтно идентичный вывод

- [x] **A1. Field-проход рендерить только при изменении входов.** Поле кодирует θ/φ поверхности
      линзы; его входы — исключительно: `sphere.bendX/bendY/width/height/depth`,
      `settings.perspective`, principal (= `vanishingPoint` + `gallery.position` + размеры) и
      размер вьюпорта/бэкинга. Ни пан, ни фазы, ни время в него не входят (проверить по
      вершинному шейдеру `HERO_FIELD_VERTEX_SHADER` — униформы только uBend/uR/uFocal/uPrincipal/
      uScreenSize). В `hero-sphere-gallery-webgl.ts`:
      - завести `let fieldDirty = true;` и ключ входов (числовая строка из перечисленных
        значений + backing size);
      - в `draw()` вызывать `passes.drawField(...)` только при `fieldDirty` (или смене ключа),
        затем сбрасывать флаг; текстура fieldTarget между кадрами сохраняется (нигде больше не
        очищается — проверить);
      - ставить `fieldDirty = true` в: `setSettings` (при изменении любого входа из списка —
        сравнение по значению), `setSize`/`resizePasses` (fieldTarget пересоздаётся),
        `handleContextRestored`, первом кадре. `captureFrame` (snapshot) ничего не меняет:
        пропуск отрисовки поля читает ту же самую текстуру.
      - Диагностика `data-hero-gallery-passes="scene→field→post"` остаётся как есть — это состав
        пайплайна, а не пер-кадровое исполнение; зафиксировать это словами в worklog.
- [x] **A2. Мемоизация `getHeroPanelZoneBounds` и его входа.** Сейчас бисекция границ зон
      считается на CPU каждый кадр, входы те же, что у поля (геометрия + principal + вьюпорт).
      В `draw()` кэшировать результат по тому же ключу, что A1 (один общий «geometry key»).
      Числа в uPanelBounds от этого не меняются ни на бит.
- [x] **A3. Ничего больше в корзине A не трогать:** scene-проход, post-проход, порядок пассов,
      расписание кадров (`schedule`), эффекты, оценщик скорости — без изменений.

## 2. Корзина B — адаптивные сэмплы чистого движения (визуальная приёмка)

- [x] **B1. Шейдер (`HERO_DISPERSION_POST_FRAGMENT_SHADER`).** Именованные константы в шапке:

      ```glsl
      const float MOTION_SAMPLE_DENSITY = 1.6; // taps per pixel of motion kernel
      const float MOTION_SAMPLE_FLOOR = 8.0;
      ```

      Перед главным циклом (сейчас `if (span < 0.5 && length(motionVelocity) < 1.5) … else`):

      ```glsl
      float motionKernel = 2.0 * length(motionVelocity);
      int activeSamples = span < 0.5
        ? int(clamp(ceil(motionKernel * MOTION_SAMPLE_DENSITY), MOTION_SAMPLE_FLOOR, float(uSamples)))
        : uSamples;
      ```

      В цикле заменить `if (i >= uSamples) break;` → `if (i >= activeSamples) break;` и
      `t = (index + jitterX) / float(uSamples)` → `/ float(activeSamples)` (то же в местах, где
      вес/страта зависят от числа сэмплов, — сверить по факту; aura-цикл не трогать: он живёт
      только в зонах). Semantics: в зонах (`span ≥ 0.5`) — ровно прежние `uSamples` (контрол
      Count — хозяин качества дисперсии); при быстром драге ядро растёт и формула сама выходит на
      `uSamples`; в покое ветка не выполняется. Меняется только полоса медленного автодвижения,
      где плотность остаётся ≥ 1.6 тапа/px против ~0.3 тапа/px в принятых зонах.
      CRT-chroma и grain автоматически масштабируются вместе с числом сэмплов — их формулы не
      трогать.
- [x] **B2. Откат/тюнинг одной константой:** `MOTION_SAMPLE_FLOOR = 8` → «16» (двукратная
      экономия вместо четырёхкратной) или `activeSamples = uSamples` (полный откат). Зафиксировать
      это в комментарии рядом с константами и в worklog.

## 4. Целевое поведение и приёмка

- **A (побайтно):** на наборе детерминированных состояний — статика без движения и эффектов;
  статика с зонами (Edge width 30, Amount 120); статика с включёнными, но спящими Grain/CRT —
  snapshot-протокол даёт **побайтно совпадающие** PNG до и после правки (одинаковые настройки,
  `advancePhases: false`). Diff = 0, не «похоже».
- **B (визуально):** стоп-кадры полосы быстрого ряда (speed 14.5) до/после + diff с усилением
  ×10: расхождения — шум внутри смаза, без структурных отличий; side-by-side видео драга и
  автодвижения — неотличимо. Быстрый драг (клип 140 px) — формула даёт `uSamples`, отличий нет.
  Пользователь смотрит и принимает лично; при сомнении — B2.
- **Перфоманс:** авторизованный замер до/после (существующий perf-харнесс репо + ручной
  Performance-трейс на машине пользователя, prod-сборка, настройки пользователя): ожидаемо
  минус один полноэкранный проход на кадр (A1) и кратное снижение стоимости post-прохода в
  полосе движущегося ряда (B1); числа — в worklog. Регрессий кадрового времени нет ни в одном
  сценарии (статика, драг, авто-прыжок, зоны, эффекты).
- **Поведение не меняется:** расписание кадров, реакция на настройки, snapshot, Rows-режим,
  эффекты, авто-скролл — как были.

## 7. Риски и отложенное

- Главный риск A1 — пропущенная инвалидация поля (устаревшие θ/φ после смены геометрии):
  закрывается общим geometry-ключом, ручной проверкой §5(а–в) и тем, что любое подозрение лечится
  сбросом флага в true (поведение = сегодняшнее). Крайний откат — рисовать поле каждый кадр, как
  сейчас.
- B меняет пиксели полосы движущегося ряда (статистически, не структурно) — принято пользователем
  как отдельная корзина с личной визуальной приёмкой и однокнопочным откатом; в зонах и при
  быстром драге вывод не меняется по построению.
- Отложено до следующих доставок и только по показаниям профиля: запечённые градиенты поля
  (минус ~3 тапа/px, но квантование упаковки), инстансинг карточек через
  `ANGLE_instanced_arrays` (если замер покажет CPU-bound), мипы текстур карточек (меняют
  сэмплирование — отдельная визуальная валидация).
- Замеры делать на prod-сборке; dev-цифры фиксировать отдельно и не сравнивать между собой.
